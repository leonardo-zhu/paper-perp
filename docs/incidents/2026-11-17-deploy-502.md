- 日期：2026-11-17

## 根因

部署是“先停旧、再起新”。空档本该只有一两秒，但下面三个问题叠加在一起：

1. **关闭时等长连接自然断开。** 旧代码在 SIGTERM 时调用 `server.close()` 并 `await` 它的回调。`server.close()` 会立刻停止接受新连接，但要等**所有已有连接**都关闭才回调；而浏览器和 Caddy 与后端之间是 keep-alive 长连接，不会主动关闭。结果是进程一直等到自己设的 10 秒强制退出（或者被 Docker 在 10 秒时 SIGKILL）。这段时间里端口已经不接新连接，新容器也还没起来。
2. **先拉 K 线再开端口。** 启动时 `await market.start()` 会先通过 REST 从 Binance 拉 500 根 K 线（r4s 要经代理），拉完才调用 `serve()`，又多出几秒端口关闭的时间。
3. **代理不等待。** Caddy 连不上上游时立刻返回 502，于是空档里的每一秒都直接变成错误页。

另外，修复过程中还有一个次生问题：Caddy 的重试配置第一次没有生效。Caddyfile 是以**单文件 bind mount** 的方式挂进容器的，在宿主机上用 `sed -i` 修改时，sed 会写一个新文件替换旧文件，inode 变了，容器挂载的仍是旧 inode，`caddy reload` 读到的还是旧内容（宿主机 inode 131098，容器内 171721）。

## 修复

**gateway（`9d55ce8`）**

```ts
// 之前
await market.start();                 // 先等 K 线
const server = serve({ ... });
// SIGTERM 时
await new Promise((r) => server.close(() => r())); // 等长连接自然断开，最长 10 秒

// 之后
const server = serve({ ... });        // 先开端口
void market.start();                  // 行情先连上，K 线放到后台加载，与实时 K 线按时间合并
// SIGTERM 时
const closed = new Promise((r) => server.close(() => r()));
server.closeIdleConnections();        // 空闲的长连接立刻断开
const hard = setTimeout(() => server.closeAllConnections(), 3_000); // 兜底
await closed;
```

在新代码下，`/readyz` 在行情就绪之前返回 503，部署流程会等它变成 200 才算成功，所以“先开端口”不会让未就绪的实例被当成可用。

**代理（`5c18150` + r4s 上的 Caddyfile）**

```
reverse_proxy 127.0.0.1:3015 {
	lb_try_duration 20s
	lb_try_interval 250ms
}
```

连不上上游时，最多等 20 秒、每 250ms 重试一次，期间请求被挂起，不返回 502。在 r4s 上通过 `docker compose exec -T caddy sh -c 'cat > /etc/caddy/Caddyfile' < Caddyfile` 原地写入，再 validate、reload，没有重建 caddy 容器，不影响同一个 Caddy 上的其他站点。

| --------------------- | ----------------- | ------------------------------------- |
| SIGTERM 到进程退出    | 最长 10 s         | 约 0.07 s（本地实测）                 |

## 经验

- 优雅关闭不能只调用 `server.close()`：keep-alive 连接会让它一直挂着，要配合 `closeIdleConnections()` 并设置兜底超时。
- 启动时先开端口，耗时的初始化放到后台，用 readiness（`/readyz`）而不是“端口有没有开”来表示服务是否可用。
- 单实例的“先停后起”一定有空档；最省事的兜底是让反向代理在短时间内重试。要做到真正零停机，需要蓝绿部署或滚动更新（新实例就绪之后再切流量）。
- 单文件 bind mount 不要用 `sed -i`、`cp`、`mv` 替换文件，要原地写入，或者挂载整个目录。
- 修完要用和故障同样的方式复现并验证（这次是边重启边高频探测），不能只看配置是否 reload 成功。

## 顺带发现：CPU 持续占满一个核

做部署后健康检查时，发现 r4s 上的 gateway CPU 一直在 60–110%（12 分钟累计 674 CPU 秒），事件循环 p99 延迟 114ms。本地同样的代码只有 4%。

- **排查**：在 r4s 上用同一镜像起了一个临时实例（3099 端口、内存数据库，不影响生产），加 `--cpu-prof` 跑了 2 分钟。CPU 占用每 30 秒依次为 29% → 42% → 40% → 52%，**随运行时间增长**。
- **根因**：profile 显示约 60% 的非空闲时间耗在 `OrderBook.top()`。它每 100ms 对**整本**上游订单簿排序一次，只为取前 25 档；而 Binance 的增量深度会不断带来远离盘口的价位，本地订单簿只增不减，排序越来越贵。本地机器快、运行时间短，所以看不出来。
- **修复**（`400e7fc`）：`top()` 改成单次遍历选出最优 N 档，不再全量排序；MarketService 在订单簿超过 3000 档时，每边只保留离盘口最近的 1000 档（展示只用 25 档，撮合受 5% 价格带限制，用不到更远的价位）；新增 `book_levels` 指标，监控订单簿大小。
- **效果**（部署后在生产上每分钟采样一次，连续 8 分钟）：

  |                   | 修复前                    | 修复后                           |
  | ----------------- | ------------------------- | -------------------------------- |
  | CPU               | 60–110%，并随运行时间上升 | 稳定在 20–22%                    |
  | 事件循环 p99 延迟 | 114–130 ms                | 20 ms                            |
  | 订单簿档位数      | 只增不减                  | 2,200–2,900（超过 3,000 就裁剪） |
  | 常驻内存          | —                         | 约 100 MB                        |

- **经验**：增量数据结构必须有上限。性能问题要在目标硬件上、跑足够长的时间再测，并用 profile 定位，不能靠猜。
